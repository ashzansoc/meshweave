## M1 — `docs/CURRENT_ARCHITECTURE_AUDIT.md`

An honest inventory of what exists today, written against the code rather than the docs.

**What already works** — verified by execution this session:
- Layer-split inference across two real hosts: Qwen2.5-0.5B, 12/12, 0.587 GiB per stage, byte-identical output to single-node.
- Node identity: generated once and persisted; signed node tokens; enrollment; stage tokens on the TCP handshake.
- Link measurement in both directions (226/228 ms, 8–15 Mbps, zero failures).
- Cluster formation with aggregate capacity explicitly labelled as distributed, not unified.
- Placement refuses rather than half-starts: VRAM, disk, published port, agent version.
- Benchmarks A/B/C: 19.02 / 16.67 / 2.93 tok/s.

**What is incomplete**
- Placement is an **even layer split** (`partition_layers`) — it ignores GPU speed, free VRAM, and link quality. This is the single biggest gap against your brief.
- No replication path: a model that fits one GPU is still split if you select two nodes.
- One request in flight per deployment; no continuous batching, no prefix caching.
- No streaming; the gateway is non-streaming.
- No mid-generation recovery or re-partitioning.
- Model coverage is Qwen2 only, by design.

**Bottlenecks, with numbers**
- Decode is 310.8 ms/token distributed against 38.8 ms single-node. The pipeline round trip is 309.8 ms against a 226–228 ms RTT, so latency dominates and compute is a few percent.
- The two metrics move in opposite directions: splitting hurts single-request TPS (6.5×) and would help aggregate only if the model did not fit.

**Abstractions worth keeping** — the agent work queue, the framing layer, `DenseConfig` geometry, the deployment planner's refusal model, the benchmark harness, the dashboard's Measured/not-measured discipline.

**Components to replace or rework** — equal-split placement; the single-request-per-deployment constraint; in-memory workload state; JSON snapshot persistence as the only store.

**Components to leave alone** — `meshweave/runtime/dense.py` (parity-verified), `stage_runner.py` transport, the process-ownership safety model.

## M2 — Research documents

Four documents, each separating **VERIFIED** (read in source) from **DOCUMENTED** from **UNKNOWN**, with file paths and URLs.

**`docs/PARALLAX_TECHNICAL_RESEARCH.md`** — pipeline-only sharding by layer range; manual layer assignment exists (`Node.manual_layer_assignment`) but node join is still mediated by its own scheduler over Lattica; relays are Gradient-operated; last release v0.1.2 (2025-12-02); no mid-generation recovery (open issue #411); no auth on ports 3000–3002; **Turing absent from its GPU database and docs**, so it falls back to placeholder 50 TFLOPS / 600 GB/s figures. Verdict: architecturally the right shape, maturity and Turing support unproven.

**`docs/DEEPSPEED_TECHNICAL_RESEARCH.md`** — evaluated as you asked, by capability rather than by one limitation:
- *Tensor parallelism*: one synchronising all-reduce per layer. At 226 ms that is ~24 × 226 ms ≈ 5.4 s/token before compute. Unsuitable for this WAN.
- *Pipeline parallelism*: **not available at inference at all** — `engine.py` raises `RuntimeError('pipeline parallelism is currently not supported in inference.')`. DeepSpeed's `PipelineModule` is a training API. So this is not a case of "PP is slow"; the inference path has none. It is the right tool for the datacenter class, where PP is not needed because NVLink makes TP viable.
- *Precision/quantisation*: fp16/bf16/int8 via HF integration.
- *Turing*: unvalidated, with open kernel issues (#8831, #8828, #8830) on small hidden sizes.
- **Retained for** future low-latency regional/datacenter clusters.

**`docs/DYNAMO_TECHNICAL_RESEARCH.md`** — platform vs backend compatibility separated:
- Platform support matrix: Ampere, Ada, Hopper, Blackwell. **Turing is not listed.**
- Backends: vLLM states compute capability 7.5+ (so vLLM itself may run on Turing); TensorRT-LLM lists no Turing; SGLang states nothing. So a vLLM worker might work while Dynamo's CUDA-13 containers and NIXL paths are unvalidated there.
- Multi-node needs etcd+NATS; disaggregation needs RDMA; no WAN/NAT story.
- It makes **no single-request decode claim** — routing and batching raise aggregate throughput, not one stream's tok/s.
- **Retained for** production serving, routing, KV-cache management and regional deployments.

**`docs/FRAMEWORK_COMPATIBILITY_MATRIX.md`** — the three frameworks plus the native runtime, scored against: model support, Turing, VRAM floor, WAN suitability, single-request effect, aggregate effect, maturity, licence, integration effort, and what Float16 would have to build. Every cell carries its evidence.

## M3 — Parallax Turing spike

The one thing the documents cannot answer, so it gets measured. Contained and reversible:

- Isolated venv at `/opt/parallax-spike/venv` on **one** node (prefer `gpu-node-1`, 15.9 GiB free), leaving `/opt/meshweave` untouched.
- Install per its docs; run **single-node** `parallax serve -m Qwen/Qwen2.5-0.5B-Instruct --dtype float16` with no published ports — Parallax ships no auth, so nothing is exposed.
- Record: install result, whether the model loads on sm_75, generation output, errors, disk used, and whether the service stays up.
- Stop the service afterwards; leave the venv and document how to remove it.
- No multi-node test in this milestone — that needs its scheduler and relays, and would be a separate decision once Turing is settled.

If it fails on Turing, that is the result and the matrix records it.

## M4 — `docs/UNIFIED_INFERENCE_ARCHITECTURE.md`

The target design, with the two metrics as separate first-class objectives:

- **Single-request TPS** — reduce latency for one generation. Levers: don't split what fits; direct token return; prefix caching; speculative decoding (investigated, not assumed). Distribution is a last resort here.
- **Aggregate TPS** — maximise tokens across many concurrent customers. Levers: independent replicas, request routing, batching. This is where a fleet of small GPUs wins, and where Dynamo-style routing would eventually fit.

Placement by environment class, each with the measured basis and a stated default: local single GPU → replicate; same server → tensor parallel (NVLink); same rack/datacenter → DeepSpeed/FSDP-class; same city → measured pipeline; different city/country → replicate regionally unless measured otherwise.

Where each technology sits in the long-term architecture — DeepSpeed for datacenter, Dynamo for production serving and routing, Parallax as a WAN candidate if the spike passes, native runtime as the default and the fallback.
