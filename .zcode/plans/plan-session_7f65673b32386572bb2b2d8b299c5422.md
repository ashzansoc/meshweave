## MESHWEAVE Phase 2A — Connect three real Vast hosts (corrected)

All five corrections absorbed. The largest change: **direct TCP is proven before any networking software is installed**, and co-location is classified by evidence, not inferred from a shared IP.

---

### P0 — Verify SSH keys

Try `id_rsa_vastai`, `id_ed25519`, `id_rsa` against each endpoint with `BatchMode=yes`. Write `~/.ssh/config` aliases `meshweave-host-a/b/c`.

**Gate:** if no key authenticates, stop and write `docs/PHASE_2A_BLOCKED.md` with the exact key-provisioning commands. Everything downstream depends on this.

### P1 — Remote hardware inventory (EXP-NET-001, EXP-NET-002)

New `meshweave/remote/ssh.py` — async exec via `asyncio.create_subprocess_exec`, `BatchMode=yes`, per-command timeout, records exit code. Never swallows a non-zero exit.

Collect per host: `nvidia-smi`, `nvcc --version`, `python3 --version`, `uname -a`, `ip addr`, `ip route`, `ip -s link`, `free -h`, `df -h`, `ss -tulpn`, plus `dmidecode -s system-product-name`, CPU model and topology, GPU UUIDs, PCI device IDs.

GPU model verified from `nvidia-smi` — not the Vast listing.

### P2 — Direct TCP connectivity (NEW — before any overlay)

**This comes before WireGuard, per your correction.** Test all six directions using the existing Vast port mappings and the echo endpoint:

- A→B, B→A, A→C, C→A, B→C, C→B

For each: connection success, establishment time, bytes transferred, throughput, sustained-transfer stability over 60 s.

**Gate:** if direct TCP works reliably, MESHWEAVE uses persistent authenticated TCP for control and data transport and the overlay becomes optional. The overlay is only built if TCP proves insufficient. Recorded as `experiments/network/direct_tcp_matrix.json`.

### P3 — UDP capability test

Read `VAST_TCP_PORT_*` / `VAST_UDP_PORT_*` env vars and `ss -tulpn` per host. Probe UDP reachability from outside and between hosts. Test whether `/dev/net/tun` exists and whether `ssh -o Tunnel=yes` is permitted (`PermitTunnel`).

**Gate:** WireGuard only if a real UDP path exists. Otherwise SSH TUN — and if that fails, direct TCP from P2 stands as the transport. WireGuard will not be installed before this gate passes.

### P4 — Overlay deployment (EXP-NET-003), only if P3 permits

New `meshweave/network/overlay/`: `wg.py`, `tunct.py` (SSH TUN fallback, with the TUN/`PermitTunnel`/privilege checks that P3 established), `manager.py`, `addresses.py` (10.10.0.0/24 with subnet-conflict check).

Safety: never touch the SSH port's firewall rule; live SSH session during first bring-up; one-command rollback per host; verify `ssh` works before and after.

### P5 — Network benchmarks (EXP-NET-004/005/006)

- Connectivity matrix: 6 directions, route type (direct/relay), establishment and reconnection time, failure reason.
- RTT: min, avg, median, p90, p95, p99, jitter.
- Bandwidth: iperf3 (installed on hosts) plus app-level TCP. Payloads 1K/4K/8K/16K/64K/256K/1M/10M/100M. Rate-limited 1/5/10/25/50/100 Mbps plus max sustainable. Upload and download separately.

### P6 — Persistent transport tests (EXP-NET-007/008)

Four modes, real overhead measured: new connection per transfer, persistent, persistent + 4 concurrent streams, persistent + TLS. No model inference.

### P7 — Reconnection and fault detection (EXP-NET-009/010)

Kill and restart the transport path; measure detection latency and reconnection time. Impairment via `tc netem` if the container permits, else application-level — and the report says which was used.

### EXP-NET-011 — Shared public IP / co-location investigation

Dedicated experiment comparing all three pairs (A↔B, A↔C, B↔C) on hardware fingerprint and measured latency/throughput.

**Verdict scale: `same-host suspected` / `same-host confirmed` / `undetermined`.** Identical hardware fingerprints alone are not conclusive, and the report will say so. Each verdict carries its supporting evidence. If A and C are genuinely co-located they could become a fast local GPU pair — a material input to later model placement.

### Measurement accuracy (correction 4 — applies to every timing result)

- Local durations use `time.monotonic()` / `perf_counter()`, never wall clock.
- **No cross-machine one-way latency is computed** unless clock sync is established and its error measured. One-way figures are reported only as `RTT/2` and labelled as an estimate.
- Every measurement records: probe count, failed probes, warm-up period, measurement duration, and background network utilisation during the run.

### P8 — Dashboard and report

- New **Network** view: three host cards with verified GPU/VRAM, three-node graph with per-link RTT/bandwidth/jitter/loss and a direct-vs-relay badge, live status, reconnection event log.
- Link classes `LOW_LATENCY / MODERATE_LATENCY / HIGH_LATENCY / UNRELIABLE` computed from measured RTT and loss, thresholds defined in one place, never from geography.
- `docs/PHASE_2A_NETWORK_VALIDATION.md` with all 14 sections, each result tagged **measured / estimated / simulated / blocked**.

### Rules I will hold to

1. No connectivity claimed because SSH works — only measured inter-host transfer counts.
2. GPU models verified from `nvidia-smi`.
3. A and C are separate node identities, never identified by IP alone.
4. No WireGuard install before the P3 gate passes.
5. Co-location stated with a verdict and evidence, not asserted.
6. Every failed measurement recorded with its error.
7. No model loading, no inference, no pricing.
8. No destructive firewall change without a preserved SSH recovery path.

### Known risks

- **No key authenticates** → P0 gate, blocked report.
- **No `/dev/net/tun` or `PermitTunnel no`** → SSH TUN unavailable; direct TCP from P2 stands as the transport, reported honestly.
- **`tc netem` needs privileges the container may lack** → application-level impairment, stated.
- **A↔C may be fully isolated** despite the shared IP → that is a finding, not a failure.
