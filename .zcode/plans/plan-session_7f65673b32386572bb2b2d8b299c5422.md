## Float16 VDC — POC 01 plan

Four decisions were left open, so I took the recommended option in each. Each is reversible and called out here:

1. **Extend this repository in place** and rebrand the surface (UI, docs, product name) rather than porting code into a new `float16-vdc/` tree. ~60% of the brief already exists and is tested; porting buys no functionality for the POC.
2. **Keep the Python node agent.** It is deployed on both nodes, hardened, and reports NVML telemetry. The GPU worker it launches is Python regardless, so a Go rewrite would add a runtime, not remove one. It becomes a documented deviation.
3. **Keep the verified layer-split runtime as the execution path**, and run a timeboxed evaluation of Parallax rather than betting the POC on it.
4. **Gateway ships non-streaming first**, with streaming as M5b if time allows. Definition-of-Done item 8 needs one unified endpoint, not SSE.

The brief asks me not to add overlapping orchestration without a clear reason. This is that reasoning, written down.

## M1 — Infrastructure compatibility report

**Gate first:** both nodes must report agent `0.3.0` and publish a non-SSH TCP port. If either fails, I give you the one-line installer command and wait; I have no shell on those hosts.

- Run the existing RTT/bandwidth probes in both directions, persist via `POST /v1/topology`.
- Collect CUDA/driver/compute capability from NVML (already reported since the last change).
- Write `docs/VDC_INFRASTRUCTURE_REPORT.md`: per-node hardware table and per-direction network table, every cell measured or marked **blocked**.

**Acceptance:** no unmeasured value presented as fact; a verdict on whether these two links can carry a pipeline at all.

## M2 — Agent and registry hardening

- **Automatic reaping.** `CoordinatorState._reaper` is declared but never created, so a dead node stays HEALTHY until an admin calls `POST /v1/admin/reap`. Add a background task and persist on reap.
- **Authenticate the work poll.** `GET /v1/agents/{node_id}/work` accepts *any* bearer string. Verify the enrollment/node credential and return 401 otherwise; the coordinator can then hand a node a deployment it is actually allowed to run.
- **Availability projection** in the brief's vocabulary: `ONLINE / OFFLINE / BUSY / AVAILABLE / DEGRADED / MAINTENANCE`, derived from internal status plus active stages, exposed alongside the existing status. Document the mapping; don't rename the internal enum under the tests.
- **Per-node sample history** (bounded ring buffer from heartbeats) and `GET /v1/nodes/{id}/series` so GPU/VRAM can be charted over time.

**Acceptance:** tests for the 401, for reaping, and for each availability state.

## M3 — Virtual clusters

New `meshweave/coordinator/clusters.py` + routes:

- `POST /v1/clusters` `{name, node_ids}` → `F16-VDC-001`; `GET`, `DELETE`, `POST /{id}/validate`.
- **Validation at creation:** agent version, GPU present, dtype compatibility from compute capability, published port, and measured link quality between members. Memory is validated at deploy time, when the model is known — stated explicitly rather than pretending a cluster can prove it fits an unknown model.
- **Status** computed from members: `HEALTHY / DEGRADED / OFFLINE`.
- Aggregate capacity is labelled *physically distributed, not unified* in the payload itself, per the brief.
- Deployments may target a cluster; the planner expands to member nodes.
- Dashboard: Clusters view with a member diagram.

**Acceptance:** an incompatible cluster is refused with a named reason; pulling a member flips the cluster to DEGRADED.

## M4 — Two-node distributed execution (the core)

Reuses `deploy/stage_runner.py` + `meshweave/runtime/dense.py`. Work here:

- **Fix:** middle stages drop `temperature`/`top_p` for world ≥ 3 (only the last stage samples), so sampling params silently reset above two nodes.
- **Fix:** KV reservation counts all model layers on every stage, over-reserving by the node count.
- **Evidence per request, persisted:** activation bytes per hop, per-hop round trip, per-stage compute time, per-stage resident VRAM, and **NVML utilisation sampled on both nodes during generation** — the proof that both GPUs actually computed.
- **Stage handshake token:** the coordinator generates a per-deployment secret, the agent passes it via environment, and each stage verifies it in the `hello` frame. Today a published stage port accepts unauthenticated frames, which the brief explicitly warns against.
- Deploy Qwen2.5-0.5B 12/12 across both nodes (fp16 on Turing) and archive the run as JSON.

**Acceptance:** both GPUs show non-zero utilisation during the same generation; neither stage holds the full model; activation bytes traverse the wire; output text and token IDs recorded.

## M5 — Unified inference gateway

Independent ASGI app: `POST /v1/chat/completions`, `POST /v1/completions`, `GET /v1/models`, `GET /healthz`.

- API-key auth, structured request log, timeout, 503 when the cluster is unhealthy, one in-flight request per deployment with 429 beyond it.
- Routes through the existing deployment prompt queue and result channel, so the node's control surface stays closed and no new inbound port appears.
- M5b (if time allows): SSE streaming via an incremental control protocol and a chunk relay through the agent.

**Acceptance:** an OpenAI-shaped request returns a valid response; a standard client works; errors are OpenAI-shaped too.

## M6 — Network intelligence and monitoring

`meshweave/network/intelligence.py`:

- Persist measurements with history.
- **Per-strategy suitability**, not one latency threshold: for pipeline, estimated communication per token = RTT × hops + bytes/bandwidth, compared against measured compute time; classify suitable/marginal/unsuitable per strategy. Formula documented and tested.
- Dashboard: per-link history, suitability by strategy, per-node GPU/VRAM/temperature charts from the series endpoint, token throughput.

## M7 — Benchmarks and fault tolerance

`benchmarks/vdc/run_benchmark.py`, identical prompts and generation lengths:

- **A** single node 1 · **B** single node 2 · **C** distributed 12/12.
- Record tok/s, TTFT, total latency, per-node GPU/VRAM utilisation, inter-node bytes and overhead, and cost per million tokens.
- Fault experiments: stop a stage; stop an agent (node offline); force OOM; miss heartbeats; inject application-level latency (`tc` is unavailable in these containers, and the report will say so).
- Each fault records detection time and the resulting cluster state. **No claim that generation continues** after a stage dies — it cannot, and `meshweave/fault/recovery.py` already reasons that KV is unrecoverable.
